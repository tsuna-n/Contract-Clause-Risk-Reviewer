## ความครบถ้วนของผล AI

| เอกสาร | ได้คำตอบ | Provider ล้มเหลว | ผ่าน grounding judge | Citation |
|---|---:|---:|---:|---:|
| NDA ภาษาไทย TXT | 3/3 | 0 | 1/3 | 6 |
| DOCX ภาษาอังกฤษ | 3/3 | 0 | 3/3 | 4 |
| PDF ภาษาอังกฤษ | 3/3 | 0 | 3/3 | 4 |

การได้ HTTP 200 ไม่ได้แปลว่าทุกข้อผ่าน grounding: สัญญาไทยสองข้อยังไม่ผ่าน judge
จึงต้องแยกความสำเร็จของ API ออกจากความน่าเชื่อถือของผลวิเคราะห์

DOCX และ PDF ใช้ข้อความภาษาอังกฤษเดียวกัน ส่วน TXT ใช้ NDA ภาษาไทย
ความต่างระหว่าง 100.10 กับ 43.78 วินาทีจึงใช้สรุปว่า TXT ช้ากว่า DOCX ไม่ได้
นอกจากนี้เวลา AI ยังขึ้นกับ provider ที่ถูกเลือก การตอบผิด schema และ retry

ชุดประเมินใช้ `ticketscominc-sponsorship-agreement` จำนวน 8 ข้อ โดยมี gold label
สำหรับประเภท/ความเสี่ยงเพียง 4 ข้อ ผลคือ segmentation F1 100%, classification
accuracy 50%, risk accuracy 50% และ citation validity 100% ค่า citation validity
วัดว่ารหัสอ้างอิงมีอยู่จริง ไม่ได้แปลว่าทุกเหตุผลของ AI ถูกต้องหรือผ่าน grounding
ตัวอย่างที่น้อยขนาดนี้ยังใช้สรุปความแม่นยำโดยรวมไม่ได้

พบ failure ของ `clause-3` ในการรัน evaluation เวลา 22:33:52 น.: model ตอบ JSON
ที่ parse ไม่ได้จนขั้นวิเคราะห์ข้อสัญญาล้มเหลว Pipeline แยก failure ไว้รายข้อและ
endpoint ยังตอบ HTTP 200 จึงต้องจัดผล evaluation เป็น **สำเร็จบางส่วน** ไม่ใช่ผ่านครบ
ตาราง raw JSON ระบุ `passed` ตามเงื่อนไข HTTP status ของตัวจับเวลาเท่านั้น
อ้างอิงรายละเอียดที่ [บันทึกข้อผิดพลาดของ AI](benchmark-ai-findings-2026-09-07.json)

log มีการ retry ระดับ LLM client 3 ครั้งระหว่างการทดสอบ การประเมินความเสี่ยง
หนึ่ง call ใช้เวลาถึง 161.61 วินาทีเมื่อรวมการทำงานภายใน call นั้น จึงเป็นจุดที่ทำให้
เวลารอผันผวนมากกว่าการอ่านไฟล์หรือฐานข้อมูล Stage timings เป็นเวลาของแต่ละงาน
ซึ่งมีส่วนที่ทำพร้อมกัน จึงนำผลรวม stage มาบวกแทนเวลารอของผู้ใช้ไม่ได้

Google OAuth ยังไม่ได้จับเวลาการกรอกรหัสผ่าน ให้ consent และ callback ด้วยบัญชีจริง
การจับเวลานี้ไม่ครอบคลุมเครือข่ายภายนอกของผู้ใช้จริง โทรศัพท์มือถือ ผู้ใช้พร้อมกันหลายคน
หรือฐานข้อมูลที่มีประวัติจำนวนมาก การทดสอบ browser จับเวลาเปิดหน้า Playbook และ
Evaluation ส่วนการเรียก CRUD และรัน evaluation จับเวลาที่ API
